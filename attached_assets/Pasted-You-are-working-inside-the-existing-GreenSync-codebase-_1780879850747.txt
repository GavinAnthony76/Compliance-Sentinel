You are working inside the existing GreenSync codebase.

GreenSync is a production-ready multi-tenant SaaS platform for lawn care and landscaping businesses. It already includes company users, platform admins, customer portal, public booking pages, Stripe billing, SendGrid, Twilio, customer management, scheduling, estimates, invoices, routes, automations, reporting, and tenant isolation through companyId.

The app is built as a TypeScript pnpm monorepo with:
- Express 5 API server
- React 18 + Vite frontend
- Wouter routing
- TanStack React Query
- Tailwind + shadcn/ui
- PostgreSQL
- Drizzle ORM
- OpenAPI-generated API client
- JWT auth
- Stripe
- SendGrid
- Twilio

The goal is to prepare GreenSync for real beta testers using real business data.

Security is the top priority. Do not build fast at the expense of tenant isolation, authentication, authorization, validation, logging, or safe handling of customer data.

Current architecture facts:
- All tenant business data must be scoped by companyId.
- Company users authenticate with greensync_token.
- Platform admins authenticate with greensync_admin_token.
- Customer portal users use a separate portal auth context.
- Plan gating already exists through requireFeature() and hasFeature().
- The plan map lives in artifacts/api-server/src/lib/features.ts.
- Database schema lives in lib/db.
- API routes live under artifacts/api-server.
- Frontend lives under artifacts/lawn-saas.
- Generated API client comes from lib/api-spec and lib/api-client-react.
- Use Drizzle for all DB access.
- Update OpenAPI spec and regenerate client when adding/changing endpoints.

GLOBAL BETA READINESS REQUIREMENTS
==================================================

Before implementing features, audit the codebase for:

1. Tenant isolation
- Every tenant-scoped query must filter by companyId.
- Never trust companyId from the request body.
- Derive companyId from the authenticated user/session.
- Public/customer portal token routes must only expose data explicitly tied to that customer/company.
- Platform admin routes must use authenticateAdmin, not company user auth.

2. Role authorization
- Owners/admins can manage settings, billing, team, estimates, invoices, automations, and reports.
- Staff can view assigned appointments, update job status, upload job photos, and add job notes.
- Staff should not access billing, company settings, platform admin tools, or unrelated company data.

3. Input validation
- Add Zod validation for all new request bodies.
- Reject malformed IDs, unsafe strings, missing required fields, and invalid enum values.
- Sanitize user-facing text where needed.

4. Audit logging
For all major beta actions, write activity_logs entries:
- lead created/updated
- estimate generated
- appointment checked in/out/completed
- photo uploaded/deleted
- follow-up campaign created/activated
- route optimized
- customer portal action completed

5. Error handling
- Use consistent API error shape.
- Do not leak sensitive internals in API responses.
- Log server-side details with pino.

6. Data migration safety
- Add Drizzle schema changes carefully.
- Do not destroy existing data.
- Preserve demo data.
- Add seed data for new beta features.

7. OpenAPI/client discipline
- Any new endpoint must be added to the OpenAPI spec.
- Regenerate typed client after API changes.
- Use generated hooks where practical.

8. Frontend access control
- Hide or gate pages by plan and role.
- Do not rely only on frontend gating. Backend enforcement is mandatory.

9. Beta production safety
- Add clear empty states.
- Add loading/error states.
- Add confirmation dialogs for destructive actions.
- Ensure all forms show validation feedback.
- Ensure all new features work with real data, not just mock data.
